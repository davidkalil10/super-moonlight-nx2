# hbmoonlight-host: the Moonlight host in one process

`hbmoonlight-host` does the work of `live.cjs --moonlight` in a single native process. That
command used five processes: `hbmoonlight` for stream and decode, `hbv2enc` for encode,
`live.cjs` for the ring writes, `input-feeder.cjs` and `audio-stream.cjs`. The host talks to
the console only through the launcher bridge (`smilebasic/engine/lib/bridge.cjs`), exactly as
those scripts do. `live.cjs` stays as the fallback.

```
Sunshine ──moonlight-common-c──> video.c (VAAPI/sw decode, RGB24)
                                    │ mailbox (newest frame wins)
                                    v
                      sender.c: hbv2-encode thread ── hbv2enc.c linked as is (encoder.c)
                                    │ base64 straight into a writer's request body
                                    v
                      ring-write threads x depth ──HTTP──> bridge ──> app ring slots
                      ring-poll thread (CONTROL.applied every 500 ms, keyframe on stall)
console-input.c  <──HTTP── bridge  (pad + touch, 784 bytes per frame)
      └─> LiSendMultiControllerEvent / LiSendTouchEvent
audio.c (Opus -> PCM) -> console-audio.c ──HTTP──> bridge ──> AudioOut (verified SDK calls)
```

| Part | Mirrors | Notes |
| --- | --- | --- |
| `src/bridge.c` | `shared/rpc.cjs` | libcurl, one kept-alive handle per thread, preallocated bodies; addresses as JSON numbers |
| `src/sender.c` | `live.cjs` hbv2 loop | depth, resync, cap budget for keyframes, `nextSequence` |
| `src/encoder.c` | `hbv2enc` | includes `../hbv2enc.c` unchanged; `hbv2-encode-check` proves the slots are bit identical |
| `src/console-input.c` | `input-feeder.cjs`, `controller.cjs`, `touch.cjs` | `--dry-input` prints the same lines as input-feeder |
| `src/console-audio.c` | `audio-stream.cjs` | same allocation, buffer ring, pacing, teardown and saved report |
| `src/console-layout.h` | ring, state layout, audio symbols | generated by `generate-layout.cjs`; `host-layout.test.cjs` catches drift |

The AudioOut addresses and their verify-function bytes come from
`sdk/native/audio-symbols.json` and `smilebasic/reference/sdk-checks`, through the
generated header. The host makes no console calls that `audio-stream.cjs` does not make.

Node is still needed for:
- the launcher and its bridge (the host is one of its clients);
- the fake console;
- the tests.

Pairing is `hbmoonlight pair`, which was already C. Both binaries share
`~/.config/hblauncher/moonlight`.

## Build

```
tools/moonlight/helper/build.sh ~/claude-builds/HBLauncher/moonlight-host/<build-id>   # on rig
```

The encoder is built with `-O3 -march=native` like `build-hbv2enc.sh`. A rig build runs on
m5.

## Run live (from the repo root on m5, console app open)

Step up the same way as LIVE-TEST.md, starting with video only:

```
H=~/claude-builds/HBLauncher/moonlight-host/<build-id>/build/hbmoonlight-host
$H --moonlight 192.168.8.245 Desktop --budget 96 --no-input --no-audio
$H --moonlight 192.168.8.245 Desktop --budget 96 --no-audio
$H --moonlight 192.168.8.245 Desktop --budget 64
```

- **Session dir:** defaults to the newest `runs/launcher-*`. Pass it as the first argument to pick another.
- **Options:** match live.cjs (`--size --fps --bitrate --budget --cap --qp-min --qp-max --refresh --depth --resync --threads`), plus `--labels`, `--input-hz`, `--buffer-frames`, `--queue` and `--prime`. Here `--codec` picks the Moonlight stream codec (`h264` or `hevc`). HBV2 is the only ring format, so do not pass live.cjs's `--codec hbv2`.
- **Output:** stdout carries one JSON stats line per second, as live.cjs prints, plus `writeMs`, `latencyMs`, `decodeMs` and audio counters. stderr carries events and the latency summary.
- **Threads:** `--threads 8` halves encoder CPU for about 1 ms more encode time.

## Offline comparison (fake console, m5)

`tools/moonlight/helper/compare-hosts.cjs native|node DIR CLIP` runs either host against
`fake-console/bridge.cjs`. It reports:
- fps;
- CPU per written frame, by thread (ffmpeg and hbv2enc counted as whole processes);
- frame-to-ack latency, from a complete captured frame to the bridge confirming the ring write. For live.cjs this comes from `latency-probe.cjs`.

Results at 1080p, testsrc2, depth 2, 15 s after a 4 s warm-up (2026-10-24):

| Case | Host | fps | Host CPU ms per written frame, excluding codec and ffmpeg | Codec CPU ms per written frame | Latency p50 / p99 ms |
| --- | --- | --- | --- | --- | --- |
| 5.7 MB/s link, budget 96 | Node | 44.1 | 23.9 (node) | 59.2 | 44.9 / 86.7 |
| | native | 60.1 | 1.2 | 52.0 | 20.1 / 31.5 |
| 12 MB/s, budget 64 | Node | 50.7 | 20.8 | 60.0 | 32.8 / 64.7 |
| | native | 60.1 | 1.2 | 59.7 | 8.9 / 11.2 |
| 12 MB/s, budget 96, mandelbrot | Node | 27.9 | 39.3 | 103.1 | 49.5 / 167.8 |
| | native | 60.1 | 1.2 | 92.9 | 12.5 / 15.9 |
| unlimited link, 120 fps, budget 64 | Node | 15.6 | 72.9 | 70.3 | 59.5 / 352.2 |
| | native | 119.6 | 1.2 | 72.3 | 9.2 / 14.5 |
| same, `--threads 8` | native | 120.1 | 1.2 | 47.8 | 11.3 / 17.8 |

- **Node overhead:** in Node, the main thread costs 20-70 ms CPU per frame. Most of it comes from the capture loop concatenating 64 KiB pipe chunks into a 6 MB frame and from base64 and JSON. The native host spends about 1.2 ms per frame outside the codec (1.1 of that is reading the ffmpeg pipe). The sender and its buffers are allocated up front, so nothing is allocated per frame except inside libcurl, ffmpeg and hbv2enc.c.
- **Codec cost:** the codec costs the same in both. With OpenMP's default thread count it is about 4 ms of wall time and 50-90 ms of CPU per frame. `--threads 4` cuts that to 28 ms of CPU at 7.6 ms of wall time.
- **120 fps:** at 120 fps on an unlimited link, encode (4.6 ms) plus write (3.0 ms) fits the 8.3 ms frame period. CPU is divided by written frames. Node captured 120/s but wrote only 15.6/s, so its per-written figures overstate the cost per captured frame (by about 25% in the 5.7 MB/s row).
- **Full session:** video, 60 Hz input and audio together on the 5.7 MB/s fake link run at 59.7 fps with budget 64, with 0 audio underruns. With budget 96 the same session drops to 44 fps. In the fake model every input read and audio call costs one full exchange.
- **Input parity:** `--dry-input` and input-feeder.cjs print identical lines on `bridge.cjs --pad`, in both layouts.
- **Audio parity:** the native audio path and audio-stream.cjs play an 8 s file with the same counters: 100 appended, 0 underruns.

## Known gaps

- Not run against a real console or Sunshine yet. The first live run should follow LIVE-TEST.md.
- `hbv2enc.c` still allocates per frame inside `globalMotion` and `deferToCap`. Its `fail()` exits the whole host, where before it only ended the hbv2enc child. Both stay as they are so the codec remains bit identical to hbv2enc.
- On a failed AudioOut call the host stops audio the way audio-stream.cjs does: StopAudioOut and no Close. Video keeps going.
- Bridge requests time out after 60 s (libcurl), where live.cjs waits forever. This only matters if the link itself dies.
